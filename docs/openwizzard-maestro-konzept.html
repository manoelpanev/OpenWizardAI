OpenWizzard × Maestro

Konzept · Stand 23.09.2026 · Basis: Maestro 0.17.5 (AGPL-3.0, 4.616 Dateien)

Maestro wird als Fork zum Desktop-Client von OpenWizzard. Alle Funktionen bleiben erhalten. Sie werden den PurpleDragon-Modulen zugeordnet und über Spiel-Level freigeschaltet.

Kurzfassung

Was

Fork statt Neubau

Maestro liefert bereits etwa 80 % von „Command Deck“ und „Agent Desk“: Multi-Agent, Auto Run, Group Chat, Analytics. Neu dazu kommen nur Login, Entitlements und XP.

Wo

Eine zentrale Stelle

Maestro schaltet Features schon heute über „Encore Flags“ (resolveEncoreFeatures()). Genau hier wird der Entitlement-Service angeschlossen.

Spiel

XP aus echter Arbeit

Die lokale Statistik-DB (Queries, Auto-Run-Minuten, erledigte Tasks) liefert Events an den Game-Service. Achievements wandern auf den Server.

Pflicht

AGPL-3.0 beachten

Der Client-Fork muss Open Source bleiben, inklusive Hinweis auf Maestro. Game- und Entitlement-Server können als eigene Dienste geschlossen bleiben. Das sollte rechtlich geprüft werden.

Was Maestro kann

Eine Electron-Desktop-App, die mehrere KI-Coding-Agents parallel steuert: Claude Code, Codex, OpenCode, Factory Droid und Copilot-CLI. Maestro reicht die Anfragen nur an den jeweiligen Anbieter durch. Deshalb laufen die KI-Kosten über das Konto des Nutzers.

Ränge

Maestros 11 Dirigenten-Ränge („Apprentice“ bis „Titan of the Baton“) werden zu Zauberer-Rängen, zum Beispiel Lehrling → Adept → Magier → Hexenmeister → Erzmagier. Die Achievement-Logik zieht auf den Server um, damit Ränge nicht lokal manipuliert werden können.

Onboarding

Der vorhandene Onboarding-Wizard und die Tour werden zur ersten Quest: „Beschwöre deinen ersten Vertrauten“. Damit wird Agent angelegt, Provider gewählt und die erste Anfrage gesendet. Das bringt Level 2.

Architektur

Die Agents bleiben lokal und nutzen die Anmeldung des Nutzers bei Claude, Codex usw. Das 3-Stufen-KI-Kostenmodell aus dem PurpleDragon-Konzept gilt nur für KI-Funktionen, die OpenWizzard selbst bezahlt, etwa einen gehosteten Group-Chat-Moderator oder Quest-Bewertung.

Risiken

Lizenz

AGPL-3.0

Client-Quellcode muss öffentlich sein, auch bei Änderungen. Der Name „Maestro“ darf nicht als Marke genutzt werden. Mit juristischer Prüfung vor dem Release klären.

Pflege

Upstream-Drift

Maestro wird sehr aktiv weiterentwickelt. Änderungen daher klein und gebündelt halten (Seam-Dateien), monatlich Upstream mergen.

Fairness

XP-Manipulation

Lokale Stats sind fälschbar. Dagegen helfen Tageslimits, serverseitige Plausibilitätsprüfung und hohe XP nur für extern prüfbare Ergebnisse (gemergte PRs).

UX

Gating nervt Profis

Power-User wollen sofort alles. Lösung: „Skip-Quest“ für erfahrene Nutzer oder frühe Level schnell erreichbar machen.

Offene Entscheidungen

  1. Fork-Strategie: Upstream-Sync halten (empfohlen) oder harter Fork?
  2. Namen: Fantasy-Namen (Vertraute, Rituale) oder technische Namen (Agents, Auto Run) in der UI?
  3. Gating-Härte: Funktionen wirklich sperren oder nur ausblenden, mit Freischaltung per Einstellung?
  4. Gehostete KI: Soll OpenWizzard eigene KI-Funktionen bezahlen (Moderator, Quest-Check) oder nur Pass-through?
